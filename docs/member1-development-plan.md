# 成员 1 基准运行部分开发计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal：** 搭好 MCPEvol-Bench 的运行流程，让固定任务能够在 Early、Middle、Late 三个环境版本下运行，保存原始日志，并供成员 2、3 接入。

**Architecture：** 优先复用基准仓库已有的模型接入、工具调用和任务运行功能，仅补充必要的配置、运行入口和日志保存。先跑通一个任务，再接入三个版本，最后与策略和评测部分联调。

**Tech Stack：** 以实际采用的 MCPEvol-Bench 版本及其依赖为准；使用基准支持的模型接口和配置格式。Python、Node 等版本按所选仓库说明安装，不自行另搭一套 Agent 框架。

**Spec：** 依据根目录的 分工.jpg、选题 4 课程说明，以及已确认的成员 1 职责。本计划按课程项目和小组现有分工编写。

## 1. 最终要做出什么

交付一个可通过命令或配置运行的基准执行流程：

```text
指定任务、环境版本和工具知识
        ↓
启动对应 MCP 工具环境
        ↓
模型接收任务并调用工具
        ↓
保存最终回答、工具调用轨迹和运行状态
```

成员 1 完成的核心标志是：同一批固定任务可以分别在三个版本下运行，运行结果能够保存，并能交给其他成员继续实验。

| 工作归属 | 负责内容 |
| --- | --- |
| 成员 1 | 环境搭建、模型与工具接入、版本选择、任务执行、原始日志、运行说明 |
| 成员 2 | 不更新、全量重写、选择性修补三种策略，以及更新后的工具知识 |
| 成员 3 | 批量对比实验、TF / PE / ECS 评分和结果汇总 |

三个人共同完成一次从“策略输出”到“运行任务”再到“评分”的联调。

## 2. 必须遵守的实验条件

- 使用 MCPEvol-Bench，并记录实际采用的仓库地址和 commit 或 release。
- 覆盖 Early、Middle、Late 三个环境版本。
- 可以使用固定任务子集；子集需要记录任务 ID，三种策略使用同一批任务。
- 最终选定任务应覆盖 Tool、Parameter、Description 三类变化；成员 1 与成员 3、4 一起确认范围。
- 三种策略保持基础模型、推理设置、任务集和 judge 协议一致。成员 1 将运行配置固定下来，成员 3 固定评分配置。
- 不微调模型，不修改基准标签。
- 三次重复是推荐设置；资源有限时允许一次，但需要由报告说明。成员 1 的试运行不等于最终完整实验。

## 3. 建议新增或整理的文件

以下路径是轻量实现建议。拿到基准代码后，如果已有相同功能，就直接复用，避免重复开发。

```text
基准仓库/
├─ member1/
│  ├─ README.md              # 环境安装、配置、运行和日志查看说明
│  ├─ run_config.example.*   # 不含密钥的运行配置示例
│  ├─ tasks_manifest.*       # 固定任务 ID、对应服务、变化类型映射
│  └─ run_tasks.py           # 必要时补充的统一运行入口
└─ outputs/                 # 原始运行日志，按运行批次区分
```

配置和任务清单采用 JSON 或 YAML 均可，优先沿用基准已有格式。`run_tasks.py` 仅在原有命令无法满足版本选择、知识加载或日志保存时补充。

## 4. 开发顺序

### 阶段 1：把环境和一个任务跑起来

**主要做什么：** 获取基准代码，按仓库说明搭建环境，接入模型和一个任务需要的工具服务。

- [x] 记录基准仓库地址、代码版本、运行环境和安装步骤。
- [x] 配好模型名称、接口地址和凭证的读取方式；配置示例使用占位符。
- [x] 选择一个依赖相对简单的任务，先在一个版本下试运行。
- [x] 确认模型实际发出了工具调用，并拿到了工具返回结果。
- [x] 保存这次运行的原始输出和报错，整理出可再次执行的命令。

**阶段交付：** 一条能够重复执行的单任务运行命令、一份日志、环境搭建说明。

**验收：** 从启动任务到最终回答或明确失败状态，整个过程有记录；可以区分模型调用失败、工具启动失败和任务执行失败。

### 阶段 2：支持三个环境版本和固定任务清单

- [x] 支持通过配置或命令选择 Early、Middle、Late。
- [x] 按真实快照切换服务版本，记录实际加载的配置与入口哈希，不能只改日志里的版本名称。
- [x] 按用户授权确定固定任务 28、144、156，记录任务 ID、服务及变化类型。
- [x] 将三项固定任务分别在三个版本试运行，共 9 次真实模型运行，服务均可启动。
- [x] 每次运行使用独立进程、工作目录与空待办登记，重置任务状态，保留本次日志。

**阶段交付：** 三个版本的启动方式、固定任务清单、各版本的试运行日志。

**验收：** 能清楚回答“这次跑了哪个任务、用了哪个服务版本、采用了什么模型和运行参数”。

### 阶段 3：接入工具知识并保存完整日志

**主要做什么：** 与成员 2 约定工具知识的传入方式，与成员 3 约定原始结果的读取方式。

- [ ] 确认工具知识的载体及加载位置，例如文件、提示词片段或基准原有知识对象。
- [ ] 支持加载成员 2 提供的工具知识，记录本次使用的知识文件或快照。
- [ ] 与成员 2 检查是否存在自动刷新工具描述、Schema 等行为，确保“不更新”策略能够保留约定的旧知识。
- [ ] 让每次运行拥有独立的 run ID 和输出位置，重复运行不会覆盖之前的结果。
- [ ] 保存原始工具调用、参数、返回结果、最终回答和错误信息；优先保留基准原有轨迹格式。
- [ ] 异常或超时的运行也保存已有轨迹，并明确标记状态。

**阶段交付：** 可加载工具知识的运行入口、日志样例、与成员 2、3 约定的输入输出说明。

**验收：** 成员 2 能将更新后的知识传入；成员 3 能从输出目录找到任务结果并送入基准评分流程。

### 阶段 4：联调并交接

**主要做什么：** 与成员 2、3 跑通小规模完整流程，整理别人能够照着操作的说明。

- [ ] 使用同一个任务，对成员 2 的三种策略分别做一次接入检查。
- [ ] 确认不同策略使用同样的任务、模型和推理设置，且没有串用知识或运行状态。
- [ ] 让成员 3 实际读取一份输出，验证能进入 TF、PE 评分流程；ECS 所需的跨版本结果也能对应到任务 ID。
- [ ] 把实际验证过的环境安装、三个版本运行命令、输出位置写入 README。
- [ ] 整理一段“运行环境与基准集成说明”，供成员 6 放入报告。
- [ ] 列出尚未解决的环境问题和受影响任务，避免将未执行的任务当作有效实验结果。

**阶段交付：** 可交接的代码和配置、运行说明、试运行日志、报告素材、已知问题清单。

**验收：** 成员 3 可以按说明自行启动任务并找到结果；成员 1 无需全程手动协助。

## 5. 与成员 2、3 的对接约定

### 成员 2 → 成员 1

成员 2 提供策略名称、该策略生成的工具知识及其加载方式；成员 1 将它们用于任务执行。更新前后的知识和更新成本由成员 2 留存，成员 1 在运行记录中关联相应文件或记录 ID。

建议统一这些输入项：

| 输入项 | 含义 |
| --- | --- |
| `task_ids` | 本次要运行的任务 ID |
| `version` | Early、Middle 或 Late，实际取值与基准配置对应 |
| `strategy` | 不更新、全量重写或选择性修补的标识 |
| `knowledge_ref` | 具体工具知识文件、快照或对象的定位信息 |
| `run_config` | 固定模型、推理限制等运行配置 |
| `output_dir` | 本次日志保存位置 |

这些是对接项建议，不要求另写 API 服务。用现有函数、文件和命令传递即可。

### 成员 1 → 成员 3

每次运行至少能够定位以下内容，可直接保留在基准原有日志和一个简单的运行清单中：

| 输出信息 | 用途 |
| --- | --- |
| run ID、任务 ID、环境版本、策略标识 | 对应不同实验结果 |
| 基准代码版本、模型和推理配置、知识引用 | 核对实验条件 |
| 工具调用、参数和返回结果 | 评分与失败轨迹分析 |
| 最终回答、运行状态、错误或超时信息 | 区分完成、执行失败和基础设施故障 |
| 日志路径及必要的评分输入 | 让成员 3 直接进入评测流程 |

## 6. 重点检查的五类问题

- [ ] **版本切换无效：** 运行记录能证明实际使用了哪个服务配置；无法切换时明确报错。
- [ ] **知识自动刷新：** 与成员 2 确认加载内容，避免旧知识被运行器悄悄替换。
- [ ] **状态残留：** 重复运行或切换策略后，任务数据和知识不会意外沿用上一轮状态。
- [ ] **异常导致日志丢失：** 模型接口出错、工具返回错误或超时后，仍能找到已经产生的轨迹。
- [ ] **日志无法评分或被覆盖：** 成员 3 实际读取样例进行验证；重复运行保留不同批次的结果。

上述检查以少量试运行和联调验证即可，优先复用基准已有检查方式。

## 7. 时间安排建议

建议争取用约 2 个开发日打通并交接；依赖安装和服务问题可能影响时间，因此按下列顺序推进。

| 时间段 | 优先完成 | 给其他人的输出 |
| --- | --- | --- |
| 第 1 天前半段 | 阶段 1，跑通单任务 | 给成员 2、3 提供初步运行方式和日志样例 |
| 第 1 天后半段 | 阶段 2，支持三个版本 | 给成员 3 提供任务与版本配置 |
| 第 2 天前半段 | 阶段 3，知识接入和日志完善 | 与成员 2 固定知识加载方式，与成员 3 固定结果格式 |
| 第 2 天后半段 | 阶段 4，联调和交接 | 提供可运行代码、说明、日志和已知问题 |

若环境搭建受阻，及时把具体依赖、错误和受影响服务告知成员 3、4，一起调整固定任务范围，并维持三类变化覆盖。任务范围在正式对比前确定，不能根据哪个策略得分更好来挑任务。
